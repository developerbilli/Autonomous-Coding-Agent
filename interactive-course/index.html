MODULE 03

The LangGraph Brain

How graph state machines prevent AI from entering infinite loops

Every developer who has played with AI agents has experienced the Infinite Loop of Despair.

The AI tries to fix a bug. It makes a typo. It tries to fix the typo, but breaks another file. It tries to fix that, and before you know it, it has spent $80 in API tokens, deleted half your repository, and left you with completely broken code.

To fix this, we built our workflow as a formal state graph using LangGraph. Think of a busy railway switching yard: trains can only travel along laid tracks, signals prevent collisions, and the central switchboard routes each train according to strict rules.

🛤️

The Deterministic Spine

The first steps (Explore → Plan → Code → Test → Sandbox) are 100% hardwired. The AI is never allowed to hallucinate early steps or skip writing tests.

🔀

Conditional Remediation Edges

Only after real tests run does the Manager make a dynamic routing choice: route to Debugger on failure, or route to Reviewer on success.

⏱️

Centralized Retry Metering

Every repair loop increments a single shared budget. Once iteration_count >= 3, the agent is blocked from looping and fails closed safely.

💾

SQLite WAL Checkpointing

Every single step is saved to a persistent SQLite database with WAL mode. If your laptop loses power, it resumes right where it left off.

The "Aha!" Insight: Why Centralized State Beats Message Passing

In rookie agent systems, Agent A texts Agent B, who texts Agent C, who texts Agent A. Soon, messages get duplicated, nobody knows who has the latest code, and state is lost. In our architecture, agents use a Blackboard State: they write their results to a central ledger (`AgentState`). Any agent can inspect history, diffs, and test results cleanly without telephone-game degradation.

MODULE 04

AST Code Map & Sandbox

How the agent understands huge codebases and executes code without destroying your computer

Here are the two biggest engineering hurdles in autonomous coding:

🗺️

The Context Window Trap

A real codebase has hundreds of files and tens of thousands of lines. If you stuff everything into the prompt, the AI gets confused, ignores instructions, and costs a fortune.

☣️

The Execution Hazard

When an AI generates code, that code has to be executed to run unit tests. What if the AI generated an infinite loop, or a line that deletes your home directory?

We solved both problems with two foundational technologies: the AST (Abstract Syntax Tree) and an Isolated Docker Sandbox.

💡

The "Aha!" Insight: AST vs. Naive Search (Grep)

Why not just use regular text search for words like def calculate? Because regular search is blind. If the word calculate appears in a comment, an old docstring, or a variable name, text search gets tricked. An AST understands Python grammar. It knows whether a function is inside a class, what decorators wrap it, and who calls it.

The Biosafety Cleanroom: How the Sandbox Protects You

When pytest runs, it executes inside an ephemeral Docker container locked down with five strict shields:

SHIELD 1 Dropped Capabilities

Runs with --cap-drop=ALL so generated code has zero administrator or kernel privileges.

SHIELD 2 Network Blackout

Runs with --network=none so tests cannot leak environment variables or call external webhooks.

SHIELD 3 Read-Only Root

Mounted with --read-only so the container OS cannot be modified or infected.

SHIELD 4 Memory & CPU Caps

Capped at 512MB RAM and 1 core, preventing accidental infinite loops from freezing your machine.

Almost all of them let the AI declare victory on its own. When the AI gets tired or confused, it simply outputs "DONE! Everything works!" and the pipeline ends. If a sneaky bug slipped through or an existing test was accidentally deleted, nobody notices until production goes down.

In our architecture, the Manager LLM has zero authority to declare success. Success is decided solely by the IndependentVerifier.

The TOCTOU Race Condition: The Split-Second Danger

What is TOCTOU? Imagine the verifier checks your files at 12:00:00. While the system spends 5 seconds compiling the final report, a background process or file watcher alters app.py at 12:00:03!

We defeated this with two safeguards: 1) Pre-report re-verification that regenerates the report if drift occurred, and 2) Atomic Immutable Handovers: packaging verified files into a sealed, read-only .tar.gz archive (with permissions locked to chmod 0o444) and sealed with a SHA-256 digest. Downstream systems deploy from the sealed archive, permanently immune to working-tree drift!

CODE (agent/verification/verifier.py) 
def create_immutable_handover(self, manifest):
    archive_path = handover_dir / f"verified_handover_{digest[:12]}.tar.gz"
    with tarfile.open(archive_path, "w:gz") as tar:
        for rel in sorted(manifest.keys()):
            tar.add(self.repo_path / rel, arcname=rel)
    os.chmod(archive_path, 0o444)  # Strip write bits
    artifact_hash = hashlib.sha256(archive_path.read_bytes()).hexdigest()
    return str(archive_path), artifact_hash
PLAIN ENGLISH

Generate a sealed, permanent snapshot bundle of all verified repository files.

Create a compressed tarball named with the cryptographic fingerprint of the manifest.

Pack every verified file into the archive in deterministic alphabetical order.

Lock the operating system permissions to read-only (0o444) so no process can tamper with it.

Calculate the SHA-256 digital seal and return the unalterable release artifact!
